  ### 常驻实时 MPD 是否还会付 210 ms

  分情况：

   更新内容                        是否需要重新加载/冷启动
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   当前机器人关节位置              不需要，只更新 start/boundary tensor
  ──────────────────────────────  ───────────────────────────────────────────────
   新的规划目标                    不需要，只更新 goal/EE pose tensor
  ──────────────────────────────  ───────────────────────────────────────────────
   固定环境不变                    不需要，SDF grid 持续复用
  ──────────────────────────────  ───────────────────────────────────────────────
   动态障碍物 pose 原地更新        通常不需要，但要使用动态 primitive/独立动态层
  ──────────────────────────────  ───────────────────────────────────────────────
   重建整个环境/SDF 对象           会重新产生一部分初始化成本
  ──────────────────────────────  ───────────────────────────────────────────────
   每请求重新启动 infer_once.py    会再次支付冷启动
  ──────────────────────────────  ───────────────────────────────────────────────
   更换机器人模型/checkpoint       需要重新初始化

  目前 infer_once.py 是一次请求一个进程、一次请求一个 planner，因此每次都会重新加载模型、环境并首次触发
  dense 路径。若 ROS adapter 每次都启动该脚本，210 ms 会反复出现。

  更适合实时系统的是：

  ROS/Runtime Server 启动
    ├─ 加载模型一次
    ├─ 创建环境、TorchKin、validator 一次
    ├─ warmup 8/16/32/64 一次
    └─ 循环处理请求
         ├─ copy_ 当前关节状态
         ├─ copy_ 目标
         ├─ 原地更新动态障碍物 pose
         ├─ diffusion
         └─ ranked dense replay

  现有 update_objects_extra() 会重新构建 extra-object SDF grid：MotionPlanningDiffusion/mpd/mpd/
  torch_robotics/torch_robotics/environments/env_base.py:129。它不适合高频调用。动态环境建议拆成：

  - 静态环境：保留预计算 SDF grid；
  - 动态障碍物：使用解析 box/sphere/capsule SDF，pose tensor 原地 copy_()；
  - 低频地图大改：重建 SDF，并递增 scene version；
  - CUDA Graph：scene version 或 tensor 地址变化时重新 capture。

  从当前结果看，首次 bucket 约 213 ms，而再增加两个 bucket 到检查 56 条只增加约 11 ms。这强烈暗示常驻、
  warm 后的实际 dense 增量可能只有数毫秒到十几毫秒，但需要用“同一个 planner 对象连续调用”重新测量才能给出
  可靠数字。

  所以结论是：你的判断基本正确。实时常驻进程中，210 ms 不应成为每次规划的固定成本；但前提是不能继续采用每
  请求启动 infer_once.py，也不能每次动态更新都重建完整 SDF。
